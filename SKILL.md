# freetoken

The caller owns scope, consequential decisions and independent acceptance.
Choose execution ownership before starting substantive implementation; planning
ownership does not automatically include all later coding. Finish the authorized
outcome within its scope, budgets and acceptance requirements.

This is a standalone CLI-backed workflow through this runner. Do not substitute
native workers or another dispatch skill for a selected CodeBuddy/dsh route.
Respect explicit model, effort, channel and worker-only/no-takeover instructions.

## Read the project before choosing the work

A short request, file names or a familiar task label supports only a tentative
plan. Before fixing implementation packages or executors, inspect current project
rules/state, the relevant implementation and affected call/data paths, shared
state and failure paths, and the tests that could establish acceptance. Read far
enough to explain the proposed boundary and its dependencies from concrete source;
a directory inventory alone is not evidence of independence.

Scale reading to the impact, not the prompt's length. Follow coupling when found;
do not require reading the whole repository or invent a per-file reading quota.
Existing verified context can be reused when still current. Bounded read-only
exploration may be delegated, but its output informs the caller's decomposition;
it is not a prematurely authorized implementation plan. Mark unresolved boundaries
and resolve them before dependent writes. Worker alignment is a second check, not
a substitute for caller understanding.

## Choose the work, then the executor

- After that inspection, ask whether resolving the actual coupled decisions would
  leave a coherent, potentially long, simple execution package. Settle interfaces,
  invariants and acceptance using existing interfaces, helpers and accepted
  decisions; then delegate implementation, focused tests and local repair together.
  Complexity of the project is not complexity of every package. Already-settled
  decisions do not need another formal design phase.
- Prefer backend execution for substantial work under a stable contract. Many
  files, ordered steps or a long run can fit when local choices are checkable and
  progress does not repeatedly require caller decisions. More execution volume
  does not require more design autonomy or a ladder of trivial trial tasks.
- Keep genuinely inseparable, changing design with the caller. Tiny fixes may
  also stay local when dispatch costs more than completing and checking them.
  Neither delegation quotas nor artificial batches of unrelated chores help.
- Once design stabilizes, choose the implementation owner before writing its
  first substantial patch. Reassess at meaningful boundary changes or a new
  independent outcome, not after every edit. A successful baseline is one outcome,
  not a permanent role for that worker. Record consequential routing reasons
  briefly in the existing plan/review, not a new checklist.

## Roles and context continuity

- Astra default (currently medium) owns critical exploration, design decisions,
  task fit and independent acceptance. It may implement tightly coupled work.
  Use a fresh composition reviewer when integration risk warrants it.
- CodeBuddy/dsh owns an assigned execution package: inspect the caller's draft,
  implement, test and locally repair. Start with settled, verifiable decisions;
  calibrate design autonomy from observed behavior, not project size or presumed
  model rank. A baseline test run alone proves no implementation capability limit.
- Astra low can own bounded execution once decisions and decisive checks are
  settled, including a long sequence of straightforward steps; failure of another
  worker is not a prerequisite. Prefer retaining a suitable CLI executor for its
  existing package. Verify the actual model/effort mapping; do not invent a light
  preset or silently replace an unavailable model. Difficult design returns to
  Astra default.
- Retain the implementation owner for related work while its contract and evidence
  support that route. In full mode, send batched review findings and caller-owned
  decisions back to the same worker/session within its cap. Diagnosing a defect
  does not automatically transfer implementation to the reviewer.
- Context familiarity is a reason to avoid unnecessary transfers, not to acquire
  all future work. If the caller already owns an inseparable implementation,
  finish it; assess a later stable package on its own merits. Escalate only the
  blocked scope and necessary dependencies, preserving useful work and attribution.
- A rejected lightweight run or exhausted full run may receive ONE authorized
  Astra-low repair cycle for a bounded defect under a valid contract. Another
  rejection or architectural conflict returns to Astra default. Infrastructure
  faults alone neither establish inability nor authorize takeover. Stop previous
  writers before transfer; worker-only constraints and frozen protocols prevail.
  This is normal completion routing when the user authorized the outcome without
  restricting implementation ownership; use that existing authority, not a new
  permission round. Rejection never broadens scope or overrides a required route.

Explicitly invoking `$freetoken` selects this model policy over AGENTS.md model
and effort defaults, not over scope, safety, budgets or independent checks.
Explicit task choices and higher-priority instructions prevail. State the actual
route and overridden model default before dispatch. Automatic matching does not
override project model rules; this skill cannot create tools or change your model.

## Reassess execution after decisions settle

When Astra resolves a material ambiguity, completes a diagnosis, or finishes the
judgment-heavy part of a takeover, reassess the remaining work before starting
another substantial execution phase. Base this on inspected dependencies and the
now-settled decisions, not the original task label. Escalation assigns the blocked
judgment; it does not permanently assign all subsequent execution to Astra medium.

Prefer the existing worker when it remains suitable and its protocol allows
continuation. Otherwise consider Astra low for a coherent result whose inputs,
write scope, expected checks and stop conditions can be stated from verified
context. Examples include applying a settled correction across callers, executing
a fixed validation matrix, or collecting and checking prescribed evidence. Test
oracle design, interpreting unexpected failures and deciding acceptance remain
with Astra default; “tests” or “documentation” alone does not establish low fit.
Low may execute checks, but must not weaken them or declare the whole task accepted.

Compare the remaining execution with handoff and re-reading costs. Carry a compact
handoff in the existing brief: settled decisions with source pointers, current
source/evidence identity, owned output, commands or decisive checks, and remaining
budget/stop conditions. Context familiarity alone is insufficient to retain a long
stable phase; a tiny remainder, inseparable decisions or genuinely expensive
context reconstruction can justify keeping it local. Record that reason briefly
at this boundary, without per-edit routing, utilization quotas or a new report.

A transfer still requires stopped writers and available, authorized tools. Keep
original outcome budgets and retry/repair caps: calling failed repair “routine
execution” cannot open another low cycle or revive a rejected worker round. New
ambiguity returns the affected decision to Astra default rather than prompting
low to invent policy. Zero low usage is valid when no economical bounded package
remains; reassessment is required, transfer is not.

When observed repeated planning or a missed agreed checkpoint suggests a stall,
distinguish new contract ambiguity from reconsidering settled decisions or a slow
but valid tool operation. Use the existing report or a bounded status clarification;
silence alone is not a stall. Resolve new consequential decisions with Astra;
otherwise restate the accepted contract and next reviewable result within the same
outcome. Do not add routine polling, interrupt just to obtain a progress report,
or reset limits. Batch nonblocking feedback at handback; intervene earlier for a
material decision or correctness risk.

## Select the protocol before dispatch

- Use **full** for substantial implementation expected to need independent-review
  corrections or a planned proof/integration handback. Preserve the same session
  and existing finite retry gates; reserve invocation capacity for correction.
- Use **lightweight** for a stable outcome expected to finish in one execution
  handback, including a long deterministic validation task. It retains alignment
  plus one implementation invocation (`--align --max-attempts 2`). Length alone
  does not require full mode. Unspecified substantial implementation defaults to
  full; the caller may select lightweight with a concrete single-pass rationale.
- Record the choice in the brief. These are caller protocols, not CLI mode flags.
  Never upgrade a running lightweight task, restart rejected work under a new ID,
  or switch workers to reset limits. Accepted independent work may be followed
  by a genuinely distinct package; its scope must not conceal failed leftovers.

## Execution boundaries

Use an explicit Git root, external task state and an owned write scope. Isolate
concurrent writers; `--allow` audits changes, not permissions. Preserve dirty work,
failed evidence, budgets and required target execution. Inspect settled output
and actual behavior independently: green counts or `awaiting_review` alone do not
prove correctness. For failure-prone requirements, identify the wrong behavior a
check must reject and verify that its setup actually exercises that condition.
Reconcile required checks and review findings with actual evidence before accepting
completion; missing proof remains unfinished work. This does not require mutation
testing or a new report format. Report caller-fixed work as hybrid, never
worker-only success.

Check explanations in comments and handbacks against the actual implementation;
passing tests do not validate claims about its mechanism or guarantees. Distinguish
behavioral defects, missing evidence and explanation-only corrections without
changing how attempts or rounds are counted.

Caller-written changes still receive any required independent review; discretion
about additional composition review does not waive project or task requirements.

Workers receive the brief and runner execution/report contract, not this library.
Keep the existing report format. The runner enforces mechanical checks; the caller
judges task fit, invariant preservation and acceptance.
