# 派工闭环：会话、粒度、进度与验收

日期：2026-09-11

状态：用户需求记录与设计提案；尚未实现，尚未进行模型调用验证。

## 本轮用户明确的方向

- Codex 负责规划和验收，dsh、CodeBuddy 负责执行。
- 同时考虑 token 消耗、缓存命中与执行速度。
- 任务粒度不能过小或过大，需要完整交互流程。
- 需要任务进度、超时处理、结果获取，以及验收不满意后回到原会话继续工作。

以下机制和参数是助手提案，不代表用户已批准具体实现。

## 设计原则

优化的是每个通过验收的任务所需总成本和总时间。缓存命中率只是解释指标；总 token、实际费用和订阅额度不能互相直接换算。

Codex 负责目标、边界、依赖与验收要求。工人负责局部探索、实现和自检；不要让 Codex 先完成所有实现层面的推理，再交给工人重复。

一个有独立验收结果的工作包绑定一个明确会话。返工和紧密相关的增量工作保留该会话；不相关的工作新开会话。进程可退出，会话必须可以恢复；进程活着不代表服务端缓存仍然存在。

## 缓存与上下文

- 不假设 Codex、dsh、CodeBuddy 跨服务共享缓存；即便模型相同，harness 生成的提示词、工具和路由也可能不同。
- 同一工作包尽量保持模型、profile、工具集合和固定指令稳定。新任务信息、验收反馈作为追加消息，不反复重写固定前缀。
- 原会话保留历史有助于避免重复探索，但实际缓存命中取决于提供方策略、前缀、保留时间与上下文压缩。
- 不为缓存定时发送无意义模型请求；用实测判断是否值得维持进程。
- 工人的完整工具日志保留在本地；Codex 获取阶段变化、阻塞、结束原因和结果摘要，必要时按位置读取证据。不把原始推理作为进度数据回传。
- 上下文明显偏题、压缩丢失关键约束、任务转向或重复无效返工时，保存交接摘要后换会话。不要只为了缓存继续累积无关历史。
- 费用/缓存数据未暴露时标记不可用，不由耗时猜测。OpenAI API 的缓存规则不等于 Codex 订阅额度规则。

## 工作包粒度

单位是一个可独立验收的行为变化，不是文件数、固定 token 数或固定时长。

合适示例：修复分页重复，追踪相关调用链，完成修改及必要回归检查。过小示例：先找函数、再单独派任务改条件、再派一次运行测试。过大示例：重构整个数据层并保证没有回归。

同一调用链和需要共享调查背景的修改一起派；独立目标、独立验收或互不依赖的模块分开派。如果架构或需求不确定到无法写出验收条件，先派一个有决策产物的探索任务，再在同一会话继续实现。

任务说明至少包含：目标与验收条件、工作区与起始版本、允许修改范围和排除项、关键入口/权威文档、已知条件、阻塞上报规则、时间/轮数预算、结果格式。源文件以路径与版本引用，不默认复制整仓库。脏工作区需要显式处理，不能假设新 worktree 包含未提交修改。

## 生命周期与最小状态

正常路径：待执行 → 执行中 → 待验收 → 通过。

验收不通过：待验收 → 原会话追加具体反馈 → 执行中。

异常路径：执行中 → 阻塞 / 失败 / 已取消；收到停止请求但尚未确认退出时保留“停止中”。状态不明时先核实原进程/会话，不另开写入者重做。

每个工作包记录 task_id、backend、session_id、工作区与起始版本；每轮执行另记 attempt_id、进程/连接标识、开始时间、最后事件时间、结束原因、产物路径。任务、会话和本轮进程是三个不同概念。

同一会话同一时刻只允许一个执行请求。恢复使用准确 session_id，不用“最近会话”猜测。网络断开不等于任务未被提交；重试前核实，防止重复写入或重复外部操作。

## 进度、超时与交互

进度分为传输/进程活性、工具活动、可验证里程碑。活性不等于业务进展，不虚构完成百分比。程序收集事件，不靠定时追问模型“做完了吗”。普通事件不触发 Codex 推理；阶段变化、阻塞、异常、完成或需要决策时才汇总给 Codex。

分别处理：

1. 启动超时：进程或协议未能就绪，属于接入问题。
2. 静默阈值：太久没有事件时检查活性和正在执行的命令，不直接判死。长测试或首 token 延迟可能合理。
3. 总预算：到达任务预算后请求取消/收尾，留退出宽限；必要时终止所拥有的进程树并核实停止，保存已有 diff 和日志。

阈值按任务类型和实测设置。传输层可以用程序时钟定时，持续语义验收仍需 Codex 活跃或后续明确建立的唤醒机制；skill 本身不会提供后台调度。

权限问题要显式处理：遵循派工范围和既有授权，遇到范围外动作进入阻塞；不能自动允许一切，也不能在无人可见的权限提示处永久挂起。

## 结果和返工

工人输出：完成摘要、修改文件、检查命令及结果、未执行项、剩余风险或阻塞。日志位置关联到本轮 attempt，避免把旧结果当成新结果。

退出码 0 或“已完成”只意味着可进入验收，不等于通过。Codex 对照预先约定的条件检查 diff 和必要证据，必要时重跑关键检查；并行任务还需检查整合后的行为。

返工反馈指出失败的验收条款、复现输入/错误证据、期望行为以及继续遵循的范围。例如：“空输入仍返回 500，验收要求为 400；复现见……。在原工作区修复并补该回归，保留其他正确改动。”

重复返工但无新增进展时，由 Codex 重新判断任务划分或假设，必要时交接给新会话/另一工人，不无限重试。

## 本机接口证据与接入建议

- dsh 0.1.5-rc.1 的 headless 文档：每次创建新 Agent，没有交互式后续；首 token 前无心跳，中间工具输出不打印。不能作为完整会话闭环的主入口。
- dsh ACP 文档：提供 session/new、session/list、session/resume、session/prompt、session/cancel、session/update、session/close；支持权限请求。恢复非活跃会话但不向客户端回放旧更新；需自行保留事件摘要。每会话同时仅一个 prompt；不支持 session/load。实际能力仍以 initialize 为准。
- CodeBuddy 2.147.0 帮助：支持 print、stream-json、准确 session ID 续接、轮数限制，以及后台 ps/logs/respawn；也提供 ACP。各接口之间的组合和异常行为尚未实测。

建议先用 CodeBuddy 原生非交互/续接接口验证最小闭环，再接 dsh ACP。若实测证明两者 ACP 对所需能力兼容，可共用传输实现；不要仅因协议同名就先写通用框架。

最终形式可为一个派工 skill 加薄的运行控制脚本：skill 管任务划分、判断与验收；脚本管启动、事件、计时、状态和会话定位。优先使用 CLI 已有能力，数据先用本地文件，不先建数据库、看板或常驻服务。

## 最小验证实验（尚未执行）

在临时 Git 仓库为每个候选后端运行同一个小任务：初次修改 → 查看进度 → 获取结果 → 给一条新增验收反馈 → 原会话续做 → 验收。第二轮明确作为增量要求，不把故意隐藏需求造成的返工算成工人首轮失败。

另验证取消及恢复：确认旧执行已结束、已有修改保留、session ID 正确、未出现双重写入。区分断开后重连与已经确认失败后重试。

记录首事件耗时、总耗时、Codex 协调开销、工人 token/缓存/费用（若提供）、结果正确性和人工干预。先跑单工人，再测两个独立工作包并行。与 Codex 独立完成任务比较时保持任务和验收一致。
