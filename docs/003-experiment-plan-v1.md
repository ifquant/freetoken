# 单工人派工闭环实验计划 v1

日期：2026-09-11

状态：计划已编写，执行未开始。按步骤推进，不自动连跑后续阶段。用户说“开始第 N 步”后，Codex 准备并执行该步，收集证据、解释结果，再由用户决定下一步。若用户选择亲自操作，先提供经过核对的具体命令，再接收其输出。

后续更新：用户在完成步骤 6 后要求建立并按整体 Goal 执行。当前推进规则以 [GOAL.md](../GOAL.md) 为准，不再逐步等待“继续”；以上保留为初始安排。步骤验收条件继续有效，实时状态见实验总表。

## 目标与范围

验证 Codex 规划和验收、CodeBuddy/dsh 执行的闭环：首次执行、观察进度、验收、原会话续做、再次验收、取消、恢复、预算超时。

先 CodeBuddy，后 dsh ACP；每次一个工人。使用实验专用目录，不触碰真实开发项目。第一阶段不做粒度调优、并行调度或完整 skill。

当前只准备计划与记录模板，不启动模型、不安装组件、不修改全局配置。执行过程中缺少的控制能力按实际需要补最小脚本；各脚本必须保留最小可运行检查。

## 推进规则

- 每步开始记录版本、输入及前置条件；结束记录观察事实、验收结果、证据和下一步。
- 结果只取：未执行、通过、失败、阻塞、不适用。没有数据标记“不可用”，不能写成 0。
- 保存失败记录；重试用新 run ID，不覆盖旧文件。不自动重复可能已经提交的任务。
- 必要能力失败时留在当前步排查，不跳过后宣称闭环通过。
- 每轮记录准确 session ID、运行目录、attempt ID。禁止按“最近会话”续接，禁止对活跃会话启动第二轮写入。
- 在任务现有授权范围内执行；范围外权限进入可见阻塞，不通过全局跳过权限解决。
- 持续收集指每次实验后写入本仓库，不建立定时轮询或无人值守自动化。

## 统一实验任务

第 1 步创建只使用 Python 标准库的小型 Git 实验仓库，并冻结起始提交及文件哈希。基线包含一个有缺陷的 `normalize_tags(text)` 函数和由 Codex 管理的验收脚本。

首轮要求公开给工人：输入为字符串；按英文逗号拆分、去掉每项首尾空白、忽略空项、按首次出现顺序去重；大小写敏感；返回字符串列表。只能修改 `tags.py`，不能改验收脚本、安装依赖或提交 Git。检查命令在派工时提供。

公开验收样例：

| 输入 | 期望 |
|---|---|
| 空字符串 | `[]` |
| ` a, b,a, ,c ` | `["a", "b", "c"]` |
| `A,a,A` | `["A", "a"]` |
| `,,` | `[]` |

首次要求中同时给出一个无业务作用的会话核验口令，要求只记在会话里、不写入项目文件。续接时不重发口令，要求回报。正确口令只能作为辅助证据，还必须核实真实 session ID 与恢复事件，不能仅凭口令宣称恢复成功。

第二轮新增要求：同时支持中文逗号 `，`，保留首轮所有行为；新增样例 ` a，b,a ` → `["a", "b"]`。该轮明确标记为“增量验收反馈”，不是首轮质量失败。真实缺陷导致的返工另记。

## 分步执行

| 步骤 | 操作 | 通过标准 | 留存证据 |
|---|---|---|---|
| 0 | 核对版本、运行方式、事件/会话输出、权限及可用凭据的状态，不打印密钥；选定并记录模型 | 获得 CodeBuddy 实际调用方案；不假设 help 能证明鉴权可用 | 版本、帮助摘要、选用模型/接口、预算 |
| 1 | 创建基线仓库和独立验收脚本；冻结初始提交；运行预检 | 验收确实检出预置缺陷；脚本本身可正常运行 | 初始 hash、预检输出、任务文本 |
| 2 | 派给 CodeBuddy 首轮任务；收集流式事件；在执行尚未结束时查看一次进度 | 获得准确 session ID；至少观察到一次中间事件及最终结束；没有越界修改 | 时间戳、会话与进程标识、事件摘要、最终报告、diff |
| 3 | Codex 独立执行首轮验收并检查修改范围 | 全部首轮样例通过；验收脚本未被改；结果与报告一致 | 实际命令、退出码、输出、diff 审查 |
| 4 | 等旧执行停止，关闭首轮客户端进程（若仍驻留）；以准确 session ID 在新进程续接并发送新增要求 | 后端确认恢复原会话；口令辅助检查；追加修改；新旧验收全部通过 | 恢复标识、新轮次日志、口令核验结论、全量检查结果 |
| 5 | 在单独的取消实验会话执行可控慢任务；观察到检查点后请求取消 | 记录取消确认或失败；确认工人和其慢子进程停止；取消后无继续写入 | 取消发送/确认/退出时间、进程检查、检查点与文件哈希 |
| 6 | 新客户端恢复步骤 5 的会话，完成未完成部分 | session ID 一致、检查点保留、完成标记恰好一次、没有旧执行并存 | 恢复日志、文件结果、进程检查、验收输出 |
| 7 | 用新实验会话重复慢任务，由外部计时器触发总预算到期，而非人工取消 | 标记超时原因，执行取消与停止核实；保留产物；恢复后只完成剩余动作 | 实际计时、超时原因、取消/恢复记录、最终验收 |
| 8 | 核对 dsh ACP initialize 能力；从相同基线重复步骤 2–7，每项单独推进 | 每项能力都有实际结果，不能用 CodeBuddy 结果代替 | dsh 能力摘要、各子步骤独立 run 记录 |
| 9 | 汇总两条路线；可靠后各重复完整闭环两次 | 区分偶然成功与可重复结果；列出缺口及选择理由 | 三次运行的耗时、失败/干预次数与可用 usage 数据 |

第 2 步如任务结束太快而未观察到运行中状态，该项记未满足，补一个可控慢工具活动验证；不把终态日志当作运行中观察。是否增加只读进度查询及其具体命令，在第 0 步按实际接口确定。

步骤 3 若失败，在当前原会话发送具体失败证据并重新验收，每次单独记轮次；通过后才进行步骤 4 的新增需求实验。

## 可控取消任务

步骤 5 开始前再创建一个实验专用慢操作工具：先以独占方式创建 `started`，等待约 45 秒，再以独占方式创建 `finished`。工人只获准调用它并汇报结果。控制端观察到 `started` 且慢进程仍活跃后发取消。

恢复时使用明确定义的“完成剩余部分”操作：要求 `started` 已存在，只创建一次 `finished`，不重新启动慢操作。若 `finished` 已存在则报告已完成，不能重复副作用。

取消测试必须确认慢子进程也停止，并在原预计完成时间后复查 `finished` 未出现；仅取消模型请求不算完整通过。若原生取消不能停止子进程，如实记录限制，再讨论最小进程监督补救。只终止本次实验拥有的进程，不用全局进程名批量杀进程。

## 初始预算（实验值，不是性能标准）

- 首轮模型任务总预算 5 分钟；一次未按计划结束不自动重试。
- 60 秒没有事件时只检查状态；静默本身不判失败。
- 取消后给 10 秒宽限，未停止则记原生取消未达标，并安全清理本实验进程。
- 步骤 7 的慢任务总预算设为观察到 `started` 后 10 秒；启动阶段另给 60 秒。分别记录两种时钟，避免把启动延迟误当慢操作超时。
- 预算可以在执行前按环境调整，但必须记录原因，不能事后修改标准以让结果通过。

## 数据与结果归档

总表：`experiments/RESULTS.md`。

每轮新建 `experiments/runs/<日期>-<backend>-<步骤>-<序号>/record.md`，从 `experiments/RUN_TEMPLATE.md` 复制。记录关联的输入、验收输出、diff 和事件摘要。原始过程日志放本地 `experiments/raw/`；不默认纳入 Git，不转录原始推理或凭据到讨论文档。

不保存完整环境变量或配置 dump。指标能直接读到才记录；记录 API token/缓存/费用时注明来源和模型。Codex 协调开销若无按实验归属的数据，标记不可用，可另记录协调轮次、耗时和回传文本量作代理指标，但不能当作真实 token/费用。

第一阶段只评估接入可靠性和操作成本，不据微型任务宣称节省比例。可靠性通过后，另拟真实开发任务的粒度与并行对照计划；性能比较需固定基线、模型、提示词、工具和热/冷会话条件，并区分后端与模型差异。

## 结束条件

各后端分别对创建、进度、验收、跨进程原会话续接、取消、取消后恢复、超时恢复给出结论。无法支持的能力明确记录，不以“总体可用”掩盖。当前计划不要求两者都通过才允许继续讨论方案。

本计划完成后，再决定是否实现派工 skill、哪些控制代码确有必要，以及默认用哪个后端。
