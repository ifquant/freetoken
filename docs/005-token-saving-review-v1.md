# freetoken：以 Codex 净 Token 节省为目标的改进执行计划

版本：审查与执行计划 v1.0  
审查基线：`ifquant/freetoken@bd1e8625257be653ec4386896042d6ce6f46b412`  
日期：2026-09-12  
性质：代码静态审查、已提交实验记录分析、改进设计；不是优化后的实测报告。

## 0. 结论与边界

**freetoken 已经是一个有恢复、互斥、续接和审核边界的本地派工工具，但还没有成为一个经测量证明能够节省 Codex Token 的工具。下一步的中心应当是减少 Codex 在交付完整结果过程中的总参与成本，而不是提高派工次数、扩大说明书或追求协议统一。**

建议保留 Python 标准库、已有 CLI 与单工人闭环，按“先计量 → 压缩热路径 → 自动处理机械往返 → 实测校准路由”推进。不要先建设多 Agent 平台、常驻调度服务或复杂学习型路由器。

本次已读取并分析 skill、两个运行脚本、生命周期测试、benchmark、README、交付说明及相关实验记录。仓库的源码读取成功；执行环境未能拉取可运行的完整仓库，因此没有重新运行仓库测试，也没有使用你的 Codex、dsh 或 CodeBuddy 凭据进行现场测量。下文明确区分代码可见事实、历史观测与建议目标。[R1–R9]

两个必须澄清的实现事实：当前 dsh 经 ACP 调用，而 CodeBuddy 经 `--print --output-format stream-json` 调用，并不是两条路径都走 ACP。历史对照中 CodeBuddy 记录的是 `deepseek-v4.1-flash`，dsh 记录的是 `deepseek-official/deepseek-v4-flash`；不能把这些记录解释成同一个 DS4.1 模型的跨 harness 公平比较，也不能仅凭这些记录推断模型参数规模。[R2][R7][R9]

### 最先落实的五件事

第一，建立主调用者 Codex 的 Token 账本和直接完成任务的基线。第二，把 18,934 字节的 SKILL.md 拆为短入口、运行时规则与按需故障说明。第三，默认只回传有界交付摘要，不把每个工具事件和全过程文字交给 Codex。第四，用任务契约和独立验证器承接常规执行、测试及有限返修。第五，用真实配对实验确定哪些任务应该派、哪些不该派。[R1][R2]

最终的理想交互是：**Codex 做一次边界与目标决定，worker 完成一个可验证工作包，runner 提交简短证据，Codex 做一次集中终审。**这不是取消 Codex 的责任，而是不让它承担能够被程序替代的机械协调。

## 1. 现有基础：应该保留什么

现有实现已经记录准确会话 ID、实际模型、每轮结果与用量原值；区分 `awaiting_review` 和 `accepted`；提供取消、超时、续接、调用者接管与 blocked 决策交回；通过工作区锁、前后文件哈希和过期验收拒绝机制减少并发及陈旧证据问题。测试还覆盖了部分崩溃、取消、作用域和清理情形。[R1–R4]

这些机制并非全部都是“多余开销”。错误恢复、污染的 diff、旧 worker 继续写入、遗漏用户修改，都可能诱发昂贵的 Codex 排查和返工。应减少这些机制对主模型的暴露，而不是直接删除它们。

现有文档对证据边界也比较克制：没有用 worker 的费用零值证明免费，没有用缓存比例推算 Codex 配额节省，没有把微型夹具的通过推广成大型项目验证。应继续保持这种口径。[R6][R8]

### 不应误算的成本

磁盘里保存较大的日志，本身不消耗 Codex Token；被主模型读取、通过工具返回或随后带入上下文，才可能产生相应成本。runner 在本地追加固定 worker contract，主要增加 worker 的输入，不直接等同于 Codex 输出。完整工作区哈希主要是 I/O 和时间成本，只有它引发额外观察、诊断或重试时，才进一步影响 Codex 成本。

同样，skill 不是每个请求都会完整加载。官方机制先暴露名称、描述等元数据，选中后再读取正文；是否在后续调用重复占用输入、命中缓存或被压缩，要以具体宿主的实际轨迹为准。[O1][O5]

## 3. 把目标改为可测量的约束优化

### 3.1 主目标

对同一个任务、同一初始代码和同一验收标准，定义：

`S = 1 - C_delegated / C_direct`

`C_direct` 是 Codex 直接交付到验收完成的消耗；`C_delegated` 是采用 freetoken 后，Codex 从理解任务到最终验收完成的全部消耗。二者都应包括失败后的修复、必要解释和整合，而不是只统计“开始派工到 worker 返回”的区间。

将派工成本拆为：

`C_delegated = C_skill + C_route + C_contract + C_dispatch + C_observe + C_review + C_repair + C_integrate + C_residual_context`

这些分项主要用于归因，不能通过人为分段而漏算整个主会话的实际用量。最后一项指派工材料在后续主模型调用中继续形成的上下文负担；单任务实验和多任务连续会话实验应分别观察它。

优化顺序是：在验收质量、数据授权、可恢复性和合理耗时约束下，尽量降低 Codex 消耗；随后再观察 worker 消耗和整体费用。不要把“少花 Codex”与“所有模型总 Token 最少”混为一个目标。

### 3.2 不要只保留一个 total_tokens

保留 `input_tokens`、`cached_input_tokens`、`output_tokens`、`reasoning_output_tokens`、可得的 cache-write 字段，以及字段来源和计量范围。输入/缓存输入、输出/推理输出可能存在包含关系，必须按来源定义归一化，不能直接把所有字段相加。[O2][O5]

同时保留三种独立口径：原始 Token 向量；按明确适用的模型/计费规则换算的费用或 credits；实际可观察的订阅配额变化。缺少配额映射时，将其写为未知。不能把 API 价格、另一种计费模式的 rates 或 worker 的 usage 强行换算成你的 Codex Pro 配额。[O4]

对多个任务汇总时，优先计算 `1 - sum(C_delegated) / sum(C_direct)`，同时公布任务级中位数、分位数和失败率；不要只平均每个任务的节省百分比。

### 3.3 数字示例仅解释机制

假设某任务直接交付需要 12,000 个主模型读写 Token，派工后契约、协调、审核、修补和整合合计 5,000，则净节省约 58%。另一个小任务直接只需 1,200，而派工协调需要 1,600，则反而增加约 33%。这些数字是计算示例，不是本项目的观测值。

这解释了为什么“简单”并不是正确的派工标准。应该寻找的是：**执行量足够、语义边界清楚、上下文能够独立获取、结果便宜地验证、失败后容易接管的工作包。**

## 4. 主调用者计量设计

### 4.1 先用受控 benchmark 外壳，不改造用户整个宿主

第一阶段用 `codex exec --json` 包裹完整 A/B/C 实验，读取 `turn.completed.usage`，记录线程 ID、模型、Codex 版本、skill hash、配置指纹、时间和任务 ID。官方非交互文档给出了该事件与输入、缓存输入、输出等字段。[O2]

第二阶段才考虑接入实际交互宿主：宿主提供 App Server 使用事件时，可消费 `thread/tokenUsage/updated`；读取本地会话日志则必须显式指定文件、固定解析版本和测试样例，不自动扫描用户所有历史，也不把未经确认的内部格式当成稳定 API。[O3]

**worker runner 无法仅凭自己进程里的数据，精确知道调用者 Codex 在写提示词、思考、审核时消耗了多少 Token。**计量边界必须放在调用者外层或宿主事件层。不能为了“测量”又为每个子任务启动一个额外 Codex 会话，并漏算它。

### 4.2 建议账本字段

每条用量记录至少包含 `run_id / task_id / actor / provider / model / session_id / attempt_id / event_id / source / accounting_scope / observed_at`。数值字段缺失使用 null，而不是 0。`actor` 区分 caller、worker、可选独立模型审查者。

`accounting_scope` 使用 turn、request、session_cumulative、context_occupancy、unknown 等明确值。累计值应在同一会话、同一计量定义下做差；重复事件去重，计数回退和模型变化要另开分段，不能无条件差分或简单求和。

ACP 的 `usage_update.used/size` 表示当前上下文占用和容量，可选 cost 表示累计会话成本；这不等于本轮新消耗的 Token。现有保留原值、标记口径未验证的做法应继续保留，再增加归一化层。[O6][R2]

### 4.3 轻量归因，不建立第二套昂贵推理流程

runner 记录主模型可见输出字节、调用次数、契约长度、读取证据次数和阶段标记；外层记录实际 usage。用二者对齐定位热点。分阶段 Token 在宿主不能可靠归属时明确标为代理值，不给出伪精确拆账。

Token 长度 lint 可作为开发依赖使用固定 tokenizer；无法确认实际模型编码时写 `estimated_tokens`。最终优化结论以实际 usage 为准，字符数和字节数只作稳定的辅助门槛。

## 5. 热路径瘦身：最便宜、最先可做的改造

### 5.1 SKILL.md 分层

短入口只保留：何时适用、何时直接做；怎样提出最小任务契约；一条主要运行命令；如何解读交付摘要和按需读取证据；决策阻塞、未知写入状态和验收责任等必要边界。

取消、崩溃恢复、清理、后端能力、性能实验方法和详细例子移入按需 references；非法状态、并发、陈旧证据和重试上限则继续由脚本强制处理。错误返回一个稳定错误码、简短原因及对应文档定位，而不是要求每个任务先读完整故障手册。

建议工程门槛：入口正文先以 600–1,000 estimated tokens 为目标；元数据描述先控制到约 60 estimated tokens 以内。它们是优化预算，不是普适规律，也不是已完成结果。不得为满足字数删掉关键安全或正确性约束。

压缩后不得默认要求“再读完全部 references”。否则只是把同样的开销挪了位置。调用次数、额外 `--help` 和补读说明也必须纳入测试。

### 5.2 默认终态摘要，详细事件落盘

为已有运行入口增加 `--output summary|events`，默认 summary；旧行为由 events 显式保留。`Run.event()` 仍完整写本地事件文件，但不再默认逐条 stdout 打印。调试输出也不要简单改到 stderr，因为许多宿主会把 stdout 和 stderr 一并交给模型。

保留当前同步阻塞运行与宿主执行句柄机制，避免 Codex 定期发起新的 status 调用来判断是否结束。宿主必须分段等待时，沿用同一执行句柄，并计量实际主模型唤醒次数；不能声称 CLI 阻塞就必然只有一次主模型调用。

`status --summary` 仅返回状态、运行年龄、已完成检查数和是否需要主模型介入；错误与终态响应采用固定结构。

### 5.3 把 dsh 的对话流与交付件分开

全部语义流可以继续保存在本地；`report.md` 不再直接拼接全部 `agent_message_chunk`。支持 messageId 时按消息归组；不支持时也不能把“最后一个 chunk”误当完整终稿。通过明确的最终结果结构或兼容的终稿边界提取交付摘要，无法解析时返回 `result_format_invalid`，不拿过程文字充当结论。[O6]

摘要建议包含：状态、实际变更范围、独立检查结果、风险/未完成项、证据引用及下一步动作。日志、长 diff、原始推理流均不默认回传。初始成功摘要预算可设为 250–600 estimated tokens；错误摘要设软上限并支持继续读取，不能为省 Token 隐藏失败细节。

这些长度上限限制的是信息回传，不限制必要的审查深度。高风险修改仍须打开相关实现和证据。

## 6. 从自然语言派工，升级为轻量任务契约

### 6.1 主模型只填写任务差异，固定规则由本地编译

建议新增 `TaskSpec`，但不要要求 Codex 每次手写整份复杂 schema。高频必填字段维持在 `goal / scope / acceptance`；repo、后端、模型、规则版本、通用约束和输出格式从显式选择的项目配置及模板补齐。

一个逻辑示例：

```json
{
  "schema_version": 1,
  "goal": "按已确定规则修复日志统计与 CLI 输出",
  "workspace": {"root": "/project", "baseline_ref": "<commit>"},
  "scope": {"write": ["rollup.py", "cli.py"]},
  "invariants": ["不改变公开参数名", "保留用户已有修改"],
  "context_refs": ["BRIEF.md", "rollup.py", "cli.py"],
  "acceptance": {"profile": "logrollup-v1", "check_ids": ["unit", "cli"]},
  "worker": {"backend": "dsh", "model_ref": "<confirmed-option>"},
  "limits": {"attempts": 2, "wall_seconds": 300},
  "handoff": {"decision_required": "return_to_caller"}
}
```

这是建议协议，不是仓库已有接口；300 秒和两次尝试只是例子，不应作为所有工作包的统一预算。

上下文优先使用项目相对路径、符号、行段、基线 hash 和必要约束；worker 自己读取当地代码。避免“Codex 先读全量源文件 → 生成很长转述 → worker 再读同一批文件”。但关键产品意图和反例不能只留在不可见的父会话里，必须显式传入。

固定模板由 runner 附加给 worker，不需要 Codex 在每次工具调用里重新生成；模板 hash 与完整实际输入保存在本地供审计。

### 6.2 边界：程序不能凭 schema 自动理解一切

契约不是解决所有语义问题的替代品。新架构、含糊需求、重要兼容性取舍仍由 Codex 决定。worker 可以在已确定契约内选择局部实现方法，不必每一步都请示；触及新决策才交回。

不要把读取仓库说明、worker 文本或工具日志里的任意命令直接升级为可信验收命令。检查命令来自调用者批准的 TaskSpec 或显式批准的项目 profile，以 argv 数组执行并设置 cwd、环境和超时。

## 7. 任务粒度、验证与返修

### 7.1 按验收边界切，不按文件数和“简单程度”切

| 任务形态 | 优先处理方式 | 理由 |
|---|---|---|
| 一个拼写错误、已知一行修复、可直接执行的替换命令 | 直接本地工具或 Codex 完成 | 派工解释成本可能超过剩余工作 |
| 已定规则的多处 API 迁移及关联测试 | 一个完整工作包 | 共享上下文和验收，适合摊薄交接 |
| 已定行为的 parser 扩展及 CLI 集成 | 一个完整工作包 | 按行为闭环而不是按函数拆 |
| 不确定根因的局部故障 | 必要时派一次有界取证 | 只返回事实、复现和候选解释，Codex 作关键决定 |
| 强耦合并发问题、核心安全决策、需求尚不明确 | Codex 先处理决策；再评估可外包执行量 | 不能靠长提示词把未决设计伪装成明确任务 |
| 无共享写入、可独立验证的两项工作 | 在串行净节省已成立后再试并行 | 并行主要优化墙钟，不天然减少 Codex Token |

同一个工作包内，让 worker 自行调查、实现和自检；不要固定拆成三次“调查 → 实现 → 跑测试”。只有中间确实存在调用者决策，才值得增加交接。

现有 dsh 单次记录中，完整工作包为 20.373 秒、1,270 字节报告，三轮方式为 54.284 秒、5,306 字节报告。比值约为 2.66 和 4.18；它支持减少不必要往返的假设，但没有随机化、重复充分样本和主模型完整消耗，不能推导稳定节省率。[R5][R7]

### 7.2 独立验证器让 Codex 审核“决定”，不当人工测试驱动器

runner 根据批准的 profile 自行运行格式、类型、单元、CLI 和必要集成检查，记录命令、退出码、超时、测试清单 hash、输出摘要和验证前后树状态。worker 自报测试通过不能覆盖独立结果。

验收分为三层：机械检查；契约行为检查；需要理解设计和风险的语义审查。前两层尽量由程序执行，第三层由 Codex 集中完成。测试通过不自动等于 `accepted`。保留 `awaiting_review`，或者增加与其兼容的 `ready_for_review`；不要通过重命名状态偷换责任。

固定检查定义可放在 runner 所管的外部目录，并核对 hash，减少意外改写。但当前完整权限模式下，这不是防恶意篡改的安全边界；需要对不可信任务提供此保证时必须使用外部隔离，不能把文件路径或 hash 当作沙箱。

### 7.3 常规返修可以在 worker 与 runner 之间完成

确定性的测试失败、lint 错误、有限格式错误，可由 runner 提取结构化错误摘要，反馈给原 worker，再重新验证；不必每次由 Codex 阅读、复述和重派。第一次只开放一次自动修复，观察数据后再调整，不默认耗尽现有三次上限。

反馈包括失败检查 ID、最小输入、期望与实际、必要栈帧和不变范围。同根因问题合成一包。相同错误指纹重复且没有进展、需要修改目标或验收、越界写入、会话状态不明时立即停止自动链。

接管前继续确认旧 writer 已停止，保存失败证据与部分成果。归因区分 worker 独立完成、worker 提供有效成果但 Codex 收尾、派工失败；不能把 Codex 修好的结果记成 worker 独立成功。[R1][R2]

## 8. 减少返工放大的实现改造

### 8.1 审核本次 delta，而不是反复审 HEAD 的完整差异

保留 HEAD diff 作为诊断附件，同时增加 `attempt.delta`。基线来自尝试开始时实际工作树的内容，而不只是文件 hash；需要能重建新增、删除、重命名、符号链接、二进制和已有脏文件的前后差异。

建议用按内容寻址的本地对象存储保存必要的基线内容和可重建 manifest；大文件与二进制另设本地存储预算。hash 用于身份和完整性，不能从 hash 反推出已删除文件内容。

Codex 默认收到变更文件列表、统计、关键行为变化和 delta 引用；按需读取实际 diff 与相关上下文。用户已有修改、worker 本次修改和 Codex 后续修复分别记录。验证后树发生变化，则使原验证回执失效并重新检查相关范围。

独立 worktree 只能继承提交状态的问题已经被现有文档正确指出。新增创建流程必须显式选择“要求干净基线”或“建立包含脏修改及未跟踪文件的快照基线”，不能静默忽略、stash 或重置用户代码。[R9]

### 8.2 ACP 能力与失败分类

将初始化结果编译为能力矩阵，核对版本、resume、load、close 和模型设置接口。仅调用已声明支持的可选方法；缺少 resume 时，若 load 可用且语义满足则明确降级，否则返回类型化错误，不自动创建新会话重复任务。[O7]

校验 session ID，包括权限请求所属会话；为帧大小、畸形 JSON、EOF、未知请求和取消确认增加回归测试。`used/size` 不得进入 token-spend 求和器。模型标识保存后端、provider、模型原始选项、实际确认值、CLI 版本和可得的配置。

把失败至少分为基础设施、worker 能力、契约缺失、验证失败、作用域/写入状态不明。网络 502 不应直接计为推理能力失败；发送后状态不明也不能因“网络错误”自动重发。[R3][R8]

CodeBuddy 官方已经提供 ACP 入口，但改迁 ACP 并不自动节省 Codex Token。先保留已经工作的 stream-json adapter；只有当统一传输减少维护/故障成本且不损失会话、模型和用量可观测性时，再作独立可回滚实验。[O8]

### 8.3 预算能力要如实表达

当前能可靠限制的是本地墙钟、尝试次数、后端明确支持的轮数及主模型可见输出长度。独立 skill 通常不能硬截断父 Codex 的隐藏推理消耗；不可靠的 worker usage 也不能提供可信 Token 硬限。

因此预算分为 `enforced`、`observed`、`estimated` 三类。收到可靠用量之后的停止仍可能存在在途请求和取消超调。不要把事后告警或软阈值称为准确的账单硬上限。

## 9. 实验方案：让每次改造可被证伪

### 9.1 三个主要实验组

A：Codex 直接完成，保留同样的通用工具、项目规范和环境，不引入 freetoken 正文。B：基线提交版本的 freetoken。C：改进版本。先固定一个后端和准确模型，把主要变量控制在编排方式；另一个后端作为后续复验。

另做少量“skill 已安装但不应触发”的任务，测量元数据和误触发成本。不要只选适合委派的任务，至少包含小任务、正常工作包、复杂边界任务、失败/恢复任务和不应委派任务。

第一轮用少量任务完成计量校准，不作营销结论。稳定后建立约 30–50 个不同真实任务的分层集合，可按费用预算进行重复；数量是试验设计起点，不意味着能证明很小的质量差异。复杂真实案例可来自 Rust/Python/前端改动，但项目私有源码与原始轨迹默认留在本机。

### 9.2 控制条件

同一任务从相同 commit 与相同脏状态 manifest 出发，冻结验收标准、依赖、权限条件、主模型及推理配置。随机化或交叉执行组别顺序，记录时间段和后端异常。新会话不等于冷缓存；记录缓存字段，不假装已经清空供应商缓存。[R8][O5]

验收应包含 worker 看见的检查和不作为实现提示直接提供的额外回归用例。不可把检查脚本可读性当作安全隔离保证。除了自动检查，风险较高任务还要保留相同标准的独立语义审查。

所有失败、超时、取消、格式修复、Codex 接管和整合成本都保留。最终失败的样本单独报告，不从成功样本集偷偷移除。若采用直接回退，把回退消耗算入 delegated 路径。

### 9.3 结果表与统计

每任务输出：原始 caller Token 向量、worker 用量及其质量标记、caller 调用次数、可见返回量、契约量、补读证据量、返修次数、接管类型、最终检查结果、端到端耗时、可归属费用及配额观测。

在按任务配对的差值上做 bootstrap；同一任务重复运行属于同一任务簇，不能当成完全独立的新任务。同时报告总量加权节省、任务级分布和质量差异。样本不足时公开区间和不确定性，不以一个平均值宣布胜利。

### 9.4 消融与停止条件

将“短 skill”“静默事件+短报告”“契约模板”“本地验证+有限返修”“路由规则”逐项加入，在小校准集上定位效果，再在未参与调整的任务上复验。不能一次改完再把全部收益归给某个因素。

建议试行的发布门槛：目标工作包集合上总 Codex 消耗下降至少 25%，配对统计支持真实正收益；冻结验收不新增失败；失败/接管费用已计入；不适合委派的任务能可靠回到直接路径。25% 是建议业务门槛，不是本项目现有成绩，也不保证试验一定达到。

若短 skill 和短回传之后仍没有收益，应先调整工作包范围或缩小适用场景，而不是添加新的调度层。任何关于“质量不劣超过 2 个百分点”的正式统计主张，都需要另行做样本量设计，不能从上述小样本直接得出。

建议小幅拆分现有 33,962 字节的 `scripts/freetoken.py`，而不是重写工程。模块只围绕稳定职责分离，旧脚本保留兼容入口。[R2]
